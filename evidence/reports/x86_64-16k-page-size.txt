### 页大小的两个数字（必须区分）

| 指标 | 值 | 含义 |
|---|---|---|
| `getconf PAGE_SIZE` | **16384** | 用户态 / ELF 段对齐所依据的页大小。**这才是「16 KB page size」与 Android 16 KB 兼容性要求所指的指标** |
| `/proc/self/smaps` `KernelPageSize` | 4 kB | 内核基页。x86_64 的 16 KB 模式是为兼容性测试模拟的，所以内核基页仍是 4 KB |

**由此修正了 harness 的一个真实缺陷**：`run_cubism_smoke.ps1` 原先只读 `smaps KernelPageSize`，
在 16 KB AVD 上会误报 `4 kB`。已改为**优先 `getconf PAGE_SIZE`**、仅在不可用时回退 smaps 并明确标注来源。

## 被测 APK

`CubismRuntimeSmoke-debug.apk`，27242596 B，SHA256 `710BCF176A9DD330C268B1222FBA5D1CBE17557DA646212EC464B1A2FCF1B241`
（与 API28 AVD 上通过的 APK **完全相同**）

`aapt2 dump badging` 关键行：

```
package: ... compileSdkVersion='35'
minSdkVersion:'28'
targetSdkVersion:'35'
native-code: 'x86_64'
```

`targetSdkVersion=35` 很重要：若 <35，Android 15 会为该应用启用 page-size 兼容模式（按 4 KB 装载），
本次实验就失去意义。实测为 35，因此运行在原生 16 KB 模式下。

包内 native 库：`lib/x86_64/libLive2DCubismCoreJNI.so`（116992 B）。

## 正向证据（已取得）

1. **安装成功**。Android 15 的 16 KB 设备会拒绝页对齐不合格的 APK，本 APK 两个包均 `Success`。
2. **native 库装载成功**：
   ```
   D nativeloader: Load /data/app/~~.../com.aiwatch.cubism.smoke-.../base.apk!/lib/x86_64/libLive2DCubismCoreJNI.so
     using ns clns-7 from class loader (caller=.../base.apk): ok
   ```
   无 `UnsatisfiedLinkError`、无 `dlopen failed`、无 16 KB 相关拒绝。
3. **EGL / GLES 初始化成功**：`EGL_emulation: Opening libGLESv1_CM_emulation.so` / `libGLESv2_emulation.so`。
4. **Activity 确实 resume**：运行中 `dumpsys activity activities` 显示
   `topResumedActivity=...com.live2d.demo.full.MainActivity`（因此不是「Activity 起不来」）。
5. **未观察到 native 崩溃**：logcat 无属于本 app 的 `Fatal signal` / `SIGSEGV` / tombstone；
   `/data/tombstones` 中的条目时间戳属于 systemui / GMS，与本 app 无关。

## 阻塞原因（已定位，属环境性能）

三个测试用例都在**第一个 `queueEvent` 上超时**（`gl()`，上限 20 s），完全没有产生任何 `CubismSmoke` 标记。

根因是模拟器 GL 慢到不可用：

```
D EGL_emulation: app_time_stats: avg=5236.28ms min=34.20ms max=25523.69ms count=5
```

单帧最长 **25.5 秒**。`GLSurfaceView.queueEvent` 的排队任务要等当前帧画完才执行，因此必然撞上 20 s 上限。

已尝试的缓解与结果：

| 尝试 | 结果 |
|---|---|
| 首次直接运行 | 超时（负载 52） |
| 等负载自然回落（52 → 5.1，约 10 分钟） | 仍超时 |
| 禁用 GMS / Play Store / launcher 释放 CPU（负载 19.8 → 4.6） | 仍超时；`twoModelSmoke` 变为 `shortMsg=Process crashed.`，但进程结束行是 `Killing ... due to finished inst`，即 instrumentation 收尾，**非我们代码崩溃** |

**即使放宽超时也不可行**：单帧数秒，整套 harness 有数十次 `gl()` 与多轮 12–16 次采样，
在该渲染速度下需要数小时，不能作为常规 Gate。
